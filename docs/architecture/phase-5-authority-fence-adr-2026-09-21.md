# Phase 5 authority fence — physical-schema ADR

> Date: 2026-09-21 | Mode: DESIGN | Decision: **chosen and implemented locally for the inert P5-02 storage slice only**. This is not approval to enroll NOTE users or to run a production migration.
>
> Baseline: `CardProgress` remains operational authority. The Phase 4 subject/state are derived; `subject_generation` fences topology and `mirror_revision` counts shadow writes. See [P5-00 inventory](./phase-5-p5-00-inventory-2026-09-21.md) and [full cutover design](./phase-5-authority-cutover-design-2026-09-20.md).

## Invariants before DDL

1. No row means learner mode `LEGACY`, epoch zero. A deployment of this slice alone cannot persist `NOTE` mode or change any product read/write path.
2. A learner has at most one persisted authority enrollment; a shadow subject has at most one independent authority token. The token is not `subject_generation`, `mirror_revision`, or `CardProgress.revision`.
3. Existing Phase 4 tables, historical migration `20260913_000039`, Card IDs, Card progress, events, sessions, clone overlays and external source refs are unchanged.
4. An eventual NOTE command must fence `(learner enrollment epoch, subject id, subject generation, authority revision, semantic state hash)` and commit state, complete sibling-Card projection, event/fact/receipt together. None of that runtime behavior is enabled by this ADR.

## Alternatives and decision

| Option | MySQL / ORM cost | Data and compatibility risk | Decision |
|---|---|---|---|
| Add `authority_revision` to `study_progress_subjects` | One fewer join/row on each Note Action; `ALTER TABLE` metadata lock on existing shadow table | Its current Alembic revision imports live ORM metadata, so a model change would also alter historical head-39 reconstruction unless that migration were frozen first; derived and authoritative counters would share a row | Defer. Revisit only if measured companion-row cost requires it. |
| Separate learner enrollment plus 1:1 subject token; keep current state payload in `study_progress_states` | Two small additive InnoDB tables; one extra keyed row/lock for NOTE Action; no rewrite of existing rows | Requires a precise lock order and an atomic token/state invariant at P5-04 | **Chosen for storage foundation.** Keeps history and Phase 4 meaning intact. |
| Parallel NOTE state and enrollment tables | Clean isolation at first; duplicate JSON payload, indexes and reconciliation pipeline | Two learner/Note current-state representations can drift and require a later merge | Reject for initial reversible cutover. |

The tables are `study_authority_enrollments` (`learner_user_id` PK/FK to `users`, `mode_code`, `epoch`, timestamps) and `study_authority_subject_tokens` (`subject_id` PK/FK to `study_progress_subjects`, `subject_generation`, `authority_revision`, nullable 32-byte `semantic_state_hash`, timestamps). Both have InnoDB/utf8mb4 physical contracts and nonnegative/check constraints. No large JSON is duplicated. The token's nullable hash supports a subject with no current progress; first-state semantics still require P5-04 design and tests.

## P5-01 accepted prefix: stable learner-row enrollment barrier

The enrollment row cannot itself be the first lock: by design it is **absent** for every current learner. An absent-row `SELECT ... FOR UPDATE` would rely on range/gap-lock behavior and isolation level. The always-existing `users.id` row is the stable fence. The prefix is now accepted and implemented for native direct/session/worker LEGACY flows; the external/lifecycle suffix remains incomplete.

1. Any progress-affecting transaction, including a LEGACY writer, NOTE writer, session issuance, async worker, Connect import, topology/reset/delete, or bulk maintenance path, begins by locking its learner's `users.id` **FOR SHARE**. For a multi-learner batch, lock learner IDs in ascending order before any subject/session/source/card locks. Then read `study_authority_enrollments` with a **locking/current read** (even when absent), interpret missing as `(LEGACY, 0)`, and retain the User lock until commit/rollback. A plain repeatable-read snapshot after earlier queries is not sufficient.
2. A mode/epoch transition begins with the same `users.id` **FOR UPDATE**, never by upgrading a shared lock. It waits for prior writers, blocks new writers and session issuance, rechecks eligibility and any projection/lease/job evidence while holding the exclusive fence, updates or inserts the enrollment row with a strictly increased epoch, and commits. It may not switch by a process flag. Existing issued v2/v3 work still requires an epoch-aware typed rejection or explicit drain policy; the row lock alone cannot see browser offline storage.
3. A canonical product read either holds the learner **FOR SHARE** through all state/queue/count queries or uses a proven epoch-revalidation protocol before responding. No NOTE read silently falls back to Card state. Read lock duration and switch starvation must be measured at P5-09.
4. After the learner prefix, the accepted suffix is workflow admission rows (session/batch/import/source/install) in stable identity order, subject identities in `(learner_user_id, logical_note_key)` order, token/state, shared live-Note/Card-range locks, sibling `CardProgress` in Card-ID order, contributor/availability rows, then event/fact/receipt/evidence finalization. The inert resolvers now implement the live-Note, complete CardProgress and existing contributor/availability portions; MySQL proves the Card range lock blocks a concurrent insert. Native session/worker flows take the User prefix before `StudySession`; Connect/import/clone lifecycle paths still require P5-06 alignment and fault tests before admitting NOTE.

The disposable MySQL 8.0.40 two-connection probe in `scripts/probe_p5_authority_schema_mysql.py` starts with **no enrollment row**: two User shared readers coexist; a User exclusive reader times out while one writer holds the shared lock; after release, it acquires the exclusive lock, inserts a LEGACY epoch marker, and a fresh locking reader observes it through both raw SQL and the runtime repository. This validates the stable-row prefix without requiring NOTE mode or touching configured application rows. It does **not** prove MySQL 8.0.46 production latency, the remaining Connect/lifecycle suffix, crash behavior, or deployment coverage.

The NOTE CAS token is `(enrollment epoch, subject id, subject generation, authority revision, semantic state hash)`. Its inert read/verify foundation is implemented: after the caller locks the subject, the repository locks or first-creates the token at revision zero, locks current state, initializes the token hash from exact state (or null), rejects generation/mirror/hash divergence, and validates each expected CAS component with a distinct conflict. A disposable MySQL two-connection probe confirms a competing token lock waits and times out. An inert existing-state applicator now revalidates exact raw sibling baselines, stages state plus full legacy projection and advances the token once. A separate exact evidence finalizer refreshes contributor raw bytes, availability, pointer lineage and subject aggregate hashes, then advances the still-derived `mirror_revision` once without using it as NOTE CAS. A shared no-commit history primitive validates canonical native event provenance and appends or exactly replays one scheduler-grade fact; the Phase 4 mirror uses the same encoder. The inert existing-state command now composes canonical event construction, state/token/projection, refreshed evidence and history in one caller-owned transaction. Migration 41 and its no-commit wrapper add the durable operation key, request fingerprint and exact response receipt in that transaction; MySQL proves commit and replay plus the low-level rollback behavior. It intentionally remains unexposed without the P5-05 wire/route integration and P5-06 authorization/side-effect contract; first-state creation is rejected. A first material Action on an empty subject must still atomically create state, contributor/availability evidence and advance revision `0→1`, with a null prior hash; a duplicate receipt or no-op leaves revision unchanged. Reset/rekey/delete must prevent ABA by changing generation or subject identity and refusing old tokens. Every token/state/hash and **all** sibling Card projections must commit in the caller-owned transaction. No product NOTE route or mutation is enabled by this foundation.

`20260921_000040` is deliberately **LEGACY-only** at the database level. `20260921_000041` adds only the empty authority receipt table and does not widen that constraint. An absent row is LEGACY epoch zero; even a manually inserted enrollment row cannot carry NOTE until a later migration widens `ck_study_authority_legacy_only`. This extra DDL gate prevents the partial codebase from silently serving `CardProgress` while a row claims Note authority. No automatic enrollment or receipt rows are inserted. Production deployment must use the ordinary Alembic migration path, not startup `create_all`.

## Expand → compare → cutover → contract

1. **Expand now:** create the two empty authority-fence tables and separate empty receipt table, validate pre-existing `create_all` tables fail-closed, preserve all old schemas and defaults. Each downgrade is permitted only when its owned tables are empty; ordinary incident rollback is forward repair, not DDL removal.
2. **Compare next:** P5-03 proves exact Note→every sibling `CardProgress` projection, and P5-00 refreshes production SELECT-only data/lease/traffic evidence. No NOTE enrollment.
3. **Cutover later:** after P5-04..P5-09 cover all writers/readers, issue a separate migration to admit NOTE; enforce a globally consistent enrollment lock order, revision/hash CAS, wire v4 lease fence and lossless write-through. Rehearse on production-version disposable MySQL before the first live canary.
4. **Contract later than Phase 5:** do not remove Card progress, decoders or compatibility projection while rollback depends on them.

SQLite schema tests and a disposable local MySQL 8.0.40 rehearsal passed for 39→40→41, exact table contracts, NOTE rejection, the two-connection absent-enrollment fence, empty-only downgrade/re-upgrade, receipt commit/replay and flags-off `wsgi.py` boot. The probe deleted only its generated disposable database; it did not mutate the configured application database. These are **not** proof of production-version concurrency, rollback timing, or cutover safety.

## Open decisions / needs verification

- A fresh [production aggregate and SELECT-only audit](./phase-5-p5-00-inventory-2026-09-21.md) confirm head 39, zero schema drift, zero unresolvable subjects, zero shadow rows and no unexpired server leases at one point in time. Full audit verdict is WARN, not BLOCK, due to legacy session/event anomalies requiring cohort disposition. Gunicorn Phase 4/v3/async flags were unset and Redis study queue/DLQ were empty at the observed instant; offline browser state and old/new parity remain unverified.
- P5-04/P5-06 still must prove writer-wide **suffix** lock order and coverage, first-state/reset/rekey behavior, external snapshot conflicts and authorized side effects before runtime authority code. Exact state↔token invariants, the lossless legacy encoder, composed existing-state command and P5-05 durable receipt now have focused SQLite tests plus disposable MySQL evidence; the command is still not a production route.
- The future CHECK-widening migration must be gated on all writer/reader/worker binaries being capable of failing closed for NOTE, plus MySQL fault/rollback rehearsal. An app flag alone is not an authority selector.
