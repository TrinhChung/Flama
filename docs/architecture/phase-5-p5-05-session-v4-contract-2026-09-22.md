### Numeric write profile implemented; broader qualification remains open

- **Observed / cause:** new → easy → hard was rejected by `_require_exact_legacy_float`. The guard compared f64 against binary32, but PyMySQL reads MySQL FLOAT through text conversion. `2.35` reads back as `2.35`, not `2.3499999046325684`; conversely binary32-exact `1.015625` reads as `1.01562`. The former guard was both too strict and insufficient. MySQL documents the FLOAT text conversion's `FLT_DIG` limit in [my_gcvt](https://dev.mysql.com/doc/dev/mysql-server/8.0.46/m__string_8h.html).
- **Evidence:** `scripts/probe_p5_numeric_storage_mysql.py` compares 4,107 deterministic scalar samples on local MySQL 8.0.40, including signed zero, subnormals, exponent boundaries and decimal ties. Binary32 → six significant decimal digits, nearest/ties-to-even, matches all observed read bits and remains unchanged when inserted/read again. Its separate 11-value control shows plain FLOAT → DOUBLE widening changes observed bits in seven cases. Text-copy preserves the observed values in that small control, but does not prove a concurrent migration.
- **Invariants / decision:** `note-mysql-float-text.v1` is an explicit **write-storage profile**, separate from `legacy-anki@1.0.0` evaluation. It normalizes only the four freshly calculated numeric outputs, before event construction, state hashes, receipts and sibling projection. It never rewrites an existing canonical document or historical raw baseline. The encoder still rejects any target not exactly representable under the supported MySQL text-driver contract. No DDL, production data repair, or cohort change occurs.
- **Alternatives / trade-offs:** (1) This bounded storage profile preserves the existing schema/rollback reader and legacy storage precision, at the cost of six-digit newly persisted numeric state. (2) DOUBLE expansion permits full f64 outputs but a plain ALTER breaks observed raw hashes; a safe shadow copy, concurrent-write fence, cutover and downgrade proof would be required. The profile was selected for P5's mandatory reversible projection; a future precision expansion must have its own contract/version rather than silently changing this one.
- **Cross-language implementation:** `study_note_storage_precision.py` uses binary32 plus ties-to-even decimal formatting. `noteStoragePrecision.ts` rounds the exact binary32 rational with integer arithmetic; JavaScript `toPrecision(6)` alone has different tie behavior. Twenty-three frozen scalar vectors are shared by Python and Vitest. NOTE decisions normalize all rating outcomes without changing the underlying evaluator, timestamps or UI layout.
- **Lease compatibility:** new clients advertise `accepted_note_storage_profiles`; only matching NOTE sessions receive `storage_profile` in their hashed snapshot and durable `study-session-config.v3`. Older/unprofiled v4 sessions retain config v2 and their original evaluation/receipt metadata, as do v2/v3. Unknown/missing v3 profiles fail closed; restored clients reject unknown profiles rather than discarding pending work. Direct NOTE writers use the profile and record it in native runtime provenance. Readiness now identifies `study-consumer.v2` plus the profile, so an older heartbeat cannot authorize new admission; deployment must still stop old consumers before activation.
- **Verified:** eight-action easy/hard/hard/hard/again/good/easy/good sequences pass direct REST, synchronous commit and cross-batch execution; SQLite tests compare every sibling to canonical state and prove NOTE → LEGACY rollback, with exact receipt replay for sync/async. Browser-engine tests assert the same ease sequence and sibling state. Real MySQL batch tests now use easy/hard/hard/hard, expire ORM state, compare persisted numeric values and semantic hashes, and pass competing workers, atomic fault rollback, uncertain commit and separate-process recovery. Study + Database passed 531 tests/49 files before the final capability pin; the post-pin focused run passed 158 tests, Study frontend passed 257 tests/27 files, build and targeted lint passed.

### Direct-answer retry implemented (2026-09-28)

- **Observed / cause:** identical owned-local direct NOTE requests previously returned `409 AUTHORITY_OPERATION_REUSED`: the canonical command was rebuilt with newer state/revision/server time before comparing its fingerprint. Frozen-session retry was unaffected.
- **Implemented boundary:** `study_direct_note_replay_service.py` checks a caller-intent fingerprint under the existing learner/subject fences, before stale-manifest validation or scheduler/side-effect execution. New direct receipts add a bounded `study-direct-note-replay.v1` envelope to existing response JSON, retaining the original typed canonical command and preview result. The original command fingerprint, response hash, event/history links and epoch/generation still have to agree. Replay releases its read transaction and returns the original applied state, revisions and preview; the REST route may independently prefetch a fresh next Card, so the entire HTTP body is not promised to be byte-identical.
- **MySQL finding / fix:** the first disposable MySQL run exposed JSON numeric conversion changing preview `330 / 86400` from `0.0038194444444444443` to `0.003819444444444444`, invalidating the response hash despite SQLite success. Preview JSON is now stored as canonical **text inside the envelope**, with its digest bound into the original command; decoding restores the exact result. Existing typed state tokens are unchanged. The complete receipt remains limited to 16 KiB; no DDL or historical receipt rewrite occurs.
- **Alternatives / compatibility:** reconstructing from current progress would repeat the original defect; adding another receipt table would introduce an unnecessary identity/transaction boundary. The additive existing receipt envelope was selected. Session command fingerprints are unchanged. Old/session receipts with no supported direct envelope return `AUTHORITY_DIRECT_REPLAY_UNAVAILABLE`, never become new operations. Changed body/card/key reuse, corrupt evidence and changed epochs/reset generations still reject without another event.
- **MCP contract:** `submit_review` accepts an optional stable `operation_key` for NOTE authority. Supply it on the first attempt and reuse it only for the identical answer; use a new key for a new answer. It is limited to 36 characters (UUID recommended), matching the existing MCP `ReviewEvent.client_event_id` column. Calls without a key retain server-generated event IDs; LEGACY rejects an explicit key. Server-resolved timezone/deck policy is excluded from MCP caller intent, so a preference change cannot invalidate an otherwise identical retry.
- **Evidence:** direct REST/service tests cover intervening writes, stale-manifest retries, changed input, epoch/reset fences, missing/corrupt evidence and lost acknowledgment after COMMIT. MCP JSON-RPC tests cover transport validation, stable keys, original response and unchanged legacy calls. `scripts/probe_p5_direct_replay_mysql.py` passes **15 scenarios on disposable MySQL 8.0.40**, including two synchronized independent HTTP requests (identical requests commit once; changed-body reuse conflicts), the 36-character MCP boundary and exact preview storage. Three eight-action mixed-rating flows cover direct REST, synchronous session commit and cross-batch execution, comparing reloaded sibling state/hash to canonical state and proving NOTE → LEGACY rollback. Its generated database was removed; the configured database was not modified. Final `scripts/run_tests.py --module study,database,connect_mcp --backend-only` passed **783 tests / 65 files** after the JSON-storage and MCP-key-boundary changes. Python compilation and `git diff --check` also pass. No frontend or schema changes were made in this retry slice. These results are not a full P5 release gate.

Evidence: `study_worker_service.py`, `study_session_batches`' existing status/enqueued index and the consumer regression tests.

Read transactions end before queue I/O, including failed reads.
- **Alternatives / trade-off:** A persisted claim/cursor table could reduce duplicate recovery hints but introduces another migration, lease and crash-repair lifecycle. Periodic bounded keyset sweeps reuse the existing outbox without new schema and tolerate duplicate deliveries through canonical receipt idempotency. - **Runtime:** `python study_worker.py` runs bounded queue passes and periodic outbox recovery, including when Redis is unavailable or new admission is disabled. ## Delivered contract

- Migration head `20260921_000043` admits persisted `LEGACY` and `NOTE` enrollment rows. It does not create enrollment rows or enable a cohort.
- `study-session.v4` freezes one NOTE identity per session membership: enrollment epoch, logical Note key, subject generation, authority revision and semantic state hash. v2/v3 meanings are unchanged.
- v4 issuance and synchronous commit lock the learner prefix, full subject vector, token/state and all sibling compatibility rows. Accepted actions atomically write the canonical Note state, advance the independent token, project every sibling `CardProgress`, refresh evidence, append `ReviewEvent` and history, persist receipts and native side effects.
- Frontend negotiation offers v4 first and persists/restores its authority envelope. LEGACY learners fall back to v3/v2 even when the v4 feature flag is enabled.
- Eligible direct REST and MCP review writes resolve the persisted authority route. NOTE learners use the same canonical command; LEGACY learners retain the established writer. A repeated direct `operation_key` with a different current-state request is rejected before another event is written.
- Direct Study manifest/interval reads and MCP card/queue/count reads now resolve NOTE state and per-Card availability from the canonical subject vector. Queue counts, due selection and ordering no longer execute the legacy SQL selector for NOTE learners. The read boundary verifies the full compatibility projection and fails closed on missing or divergent state/availability evidence.
- Eligible owned-local NOTE readers for Browse list/detail/tree, dashboard counts, overview/future-due statistics and the legacy study page use the same mode-aware boundary. Served NOTE counts, status and ordering are rebuilt from canonical availability instead of treating `CardProgress` as authority.
- `flask study-authority-read-audit --user-id ID` performs a read-only, fixed-observation comparison between canonical NOTE results and the rollback compatibility projection. It reports a versioned JSON PASS/BLOCK verdict and never changes enrollment.
- Explicit enrollment and rollback are transaction-neutral service operations. Both prove complete, exact legacy projection; fence the learner by incrementing epoch; reject an in-flight async batch; and cancel open leases. Rollback refuses any lossy or stale projection.
- `flask study-authority-enrollment --user-id ID --mode NOTE|LEGACY` is dry-run by default. `--apply` is required to commit. Applying NOTE additionally requires `STUDY_WIRE_V4_ENABLED=true` and `STUDY_ASYNC_BATCH_ENABLED=false`; rollback to LEGACY remains available without those forward gates.

## Original owned-local safety boundary (2026-09-23; async superseded above)

Enrollment accepts existing mirrored states with one complete compatibility row per active Card and wholly pristine owned Notes whose Cards all have no progress. Pristine enrollment creates or reuses a clean `NO_CURRENT_PROGRESS` subject, then materializes revision-zero canonical state and every sibling compatibility row atomically with complete empty history; a learner with no Notes may also enroll and roll back. A partially covered Note remains rejected because inheriting reviewed state into only the missing siblings would change legacy meaning. Logical-overlay installs, detached/quarantined/tombstoned subjects and unprojectable values also remain rejected. After enrollment, the primary owned-local REST and MCP single-Note create paths materialize the same complete shape with native provenance. Connect/Anki current-state progress snapshots and revlog history-only import are supported for enrolled Notes; legacy card-import progress and bulk content creation remain gated.

Async v4 batches remain fail-closed. v4 synchronous commit is supported, but a rollover worker needs a cross-batch frozen-token contract before it can safely advance one Note more than once. Owned-local deck progress reset has a NOTE lifecycle command with full projection validation, generation/revision fencing, session cancellation, fresh canonical/compatibility reinitialization and rollback-on-fault, so study can resume immediately after reset. Primary owned-local REST/MCP Note creation materializes canonical state before the first review; REST/MCP single-Note and MCP batch Note deletion cancel sessions, remove compatibility/content, tombstone every affected subject and advance each ABA fence. Primary REST Template creation/deletion atomically adds or detaches the projected sibling on every affected owned Note, advances subject generation without fabricating an authority revision, cancels stale sessions and preserves exact semantic state. Owned-local deck deletion applies the same full-projection validation to every contained Note, cancels covered sessions, tombstones canonical state/evidence and removes deck content in one transaction; a stale projection rolls the entire operation back. Connect/Anki current-state snapshots run under the learner fence and per-record savepoint: a material snapshot advances Note CAS once and projects every sibling; a semantic no-op only refreshes external evidence/source acknowledgement; base/local conflicts do not mutate state; finalizer faults roll back source refs, token/state and all sibling rows together. Revlog groups use the same learner/subject/compatibility locks but append immutable history facts only: current token/state/progress and mirror revision remain unchanged, replay is idempotent and a fact-finalization fault rolls back the whole source-card group. The legacy card/content package takes the learner fence before source/content/progress writes and rejects NOTE before mutation; full NOTE support waits for a canonical NoteType/Card-topology lifecycle command. Overlay/shared reset/delete and archival, admin purge, note-type bulk delete/rekey and broad MCP template mutation remain P5-06 work. NOTE overlays, admin-wide Browse, remaining integration readers, production-shaped performance and the broader fixed-context differential matrix remain P5-07/P5-09 work.

### Async admission recovery finding (2026-09-25)

- **Observed**: `StudySessionBatch` is uniquely keyed by `(session_id, batch_id)` and stores the accepted client payload/hash. Redis/local queue delivery happens after its DB commit; a crash between those steps leaves an `enqueued` row without a job. An idle worker can now reconstruct and requeue the exact LEGACY envelope from that row after validating hash, session identity/wire/snapshot and batch metadata. Duplicate deliveries are checked against the durable row, while a committed session rejects a late job.
- **Evidence**: `models/study_session_batch.py`, migrations `20260913_000037` and `20260925_000045`, `study_batch_job_from_admission()` in `app/services/study_session_service.py`, `recover_admitted_study_batches()` and `drain_study_queue()` in `app/services/study_worker_service.py`, and queue-loss/duplicate/corruption/session-state/retry-budget regressions in `tests/test_study_batch_queue.py`.
- **Potential concern**: No continuous consumer or NOTE/v4 cross-batch token writer is deployed. Recovery fairness with blocked admissions, actual Redis failures and multi-process contention still need proof. The session/batch DB locks now protect duplicate execution even when Redis leases do not, but the local probe is not a complete production durability claim.
- **Impact**: Enabling production async now could acknowledge a batch without a guaranteed worker. Migration 45 closes the retry-budget reset across crashes for admitted LEGACY jobs, but not the other async gates. The current production admission guard therefore remains in place.
- **Unknowns**: Production Redis availability, worker process topology and restart cadence need verification during P5-09; SQLite tests do not prove MySQL concurrency.
- **Alternatives considered**: (1) Keep Redis as the sole job source; this cannot recover an admission-to-push crash. (2) Reuse `StudySessionBatch` as a DB outbox and treat Redis as a delivery hint; this preserves the existing unique key/payload and avoids a second write model. A new outbox table is unnecessary unless the current row cannot carry durable retry/claim metadata.
- **Trade-offs and recommendation**: Reusing the admission row adds indexed DB scans but avoids split identity. Migration 45 adds one typed integer column instead of overloading response JSON; each failure commits a small row update under `SELECT FOR UPDATE` before another queue push. Finish durable claim/fencing semantics and NOTE/v4 canonical batch transitions rather than routing them through the Card worker. Preserve the `LEGACY` default and reversible projection until MySQL fault and rollback gates pass.
- **Migration implications**: Revision 45 expands `study_session_batches` with `attempt_count NOT NULL DEFAULT 0`, preserving all preexisting rows. Its downgrade refuses an enqueued row or any nonzero attempt count; operational cutover remains gated until a continuous consumer and MySQL restart/fault proof exist. Future claim columns would use the same expand/backfill/cutover discipline.

### LEGACY worker integrity and local MySQL proof (2026-09-25)

The execution envelope is now checked against the persisted payload, not just a copied hash. Current locking reads acquire session then batch and refresh ORM state; failure handling rechecks terminal receipts after rollback, including a commit that succeeded before its acknowledgment was lost. A zero-timeout Redis pop is nonblocking. Closed/expired sessions cannot accept new batches, while an accepted job retains recoverability after lease expiry.

The worker defers reordered event sequences without consuming retries. Cross-batch event reuse is a durable conflict, never a success acknowledgment for unprocessed events. Permanent event validation failures and missing Cards fail durably. Finalization waits for earlier admissions, rejects a failed predecessor and prevents later admission, including when the final batch contains no events.

`scripts/probe_p5_study_batch_mysql.py` verifies on disposable local MySQL 8.0.40: two connections with stale cached/read snapshots and bypassed Redis leases execute one transition; commit acknowledgment loss preserves the terminal receipt; a fresh Python process recovers a lost queue hint with its persisted retry count. `scripts/probe_p5_authority_schema_mysql.py` verifies upgrade 39→45, flags-off `wsgi.py` boot, empty downgrade/re-upgrade and migration-37 compatibility with newer `create_all` metadata. Only generated probe databases are created/dropped. These checks do not implement NOTE/v4 async, deploy a consumer, or close P5-05/P5-09.

### Internal NOTE batch continuation (2026-09-26)

- **Observed**: A v4 membership pin freezes the original Note revision/hash. After one nonfinal batch advances that Note, using the pin as the next batch's CAS expectation would reject the session's own work. Mutating the pin would instead invalidate the original snapshot and pending client events. `StudySessionBatch` already stores each immutable admitted payload/hash, and the canonical NOTE command already persists one operation receipt per accepted review.
- **Evidence**: `app/services/study_note_batch_service.py`, the internal batch context in `study_session_service.py`, read-only `require_existing_note_review_receipt()` in `study_authority_receipt_service.py`, `tests/test_study_note_batch.py` and the NOTE command section of `scripts/probe_p5_study_batch_mysql.py`.
- **Decision**: Keep the original pins unchanged. Under the session mutex, verify a contiguous, completed, nonfinal predecessor prefix and each versioned/hash-checked batch response. After canonical subject/vector locks, current locking reads verify the exact session event/command-receipt chain from the original pins. The current Note token must equal the chain's endpoint. Replay the stored **client action log** against the frozen snapshot to verify each old command fingerprint without applying it; apply only new events through the existing canonical command. This is not reconstruction of current authority from `ReviewEvent` history.
- **Atomic boundary**: New Note state/token, all sibling projections, evidence, events, history, native side effects and the completed batch receipt commit together. Nonfinal batches keep the session open; only the final batch closes it and writes `StudySessionCommit`. A fault rolls back the entire new batch, preserving completed predecessors. Terminal retry returns the stored batch receipt, including after acknowledgment loss, without another transition. A terminal receipt is historical evidence, not a promise that the Note is still at that revision.
- **Invariants**: Batch ID/payload/hash/owner/sequence/wire/snapshot/token/admission time must agree. Gaps, duplicate sequences, missing or corrupt receipts, cross-batch event reuse, epoch changes, intervening external Note writes and final batches with later admissions fail closed. Accepted work may finish after lease expiry, but an admission timestamp beyond the lease is invalid. Completed-batch retry does not require the old current-state CAS; new continuation does. The receipt query uses current reads after canonical subject/vector locks, preserving the writer's lock order even with an older MySQL repeatable-read snapshot.
- **Alternatives considered**: (1) Store a normalized mutable per-session/per-Note cursor, requiring another schema, lifecycle and atomicity contract. (2) Advance the immutable membership pin, which changes the original v4 lease meaning and is rejected. (3) Reuse the durable payload and canonical receipt chain. Option 3 is selected for this internal slice because it preserves existing identities and gives executable evidence without a second authority or new table.
- **Trade-offs / potential concern**: Every continuation replays its earlier client actions for verification, so read/CPU cost grows with the prefix and can be quadratic over many tiny batches. The internal command bounds a session to 5,000 events and 5,001 batches; this is a safety bound, not a measured capacity claim. A durable cursor/checkpoint can be considered if the measured cost requires it, while preserving receipt verification and immutable pins.
- **Unknowns / remaining gates**: This command is not connected to public admission, DB-outbox reconstruction, queue worker dispatch or continuous consumption. The current session-status reader still compares against the original pin and needs verified continuation awareness; frontend restore/rollover/finalization also needs the matching contract. Byte limits, recovery fairness, real Redis faults, process restarts for NOTE work and production-shaped contention/load remain unproven. Public NOTE/v4 admission and the legacy Card worker continue to reject NOTE; production async remains disabled. Do not enable either guard based on this internal command alone.
- **Migration / rollout implications**: No new schema or enrollment changes in this slice. It reuses migrations 43/45 and retains the full legacy projection. Reverting public rollout is unnecessary because there is no new public execution path. Do not reinterpret internal NOTE receipts as legacy worker payloads or downgrade over unfinished admitted work.

Local verification covers same-Note and interleaved-Note continuation, all-sibling projection, exact replay, an empty final batch, out-of-order work, corrupted/rehashed evidence, changed epoch, external review conflict, expired accepted work and mid-batch rollback. The disposable MySQL 8.0.40 probe additionally proves two competing internal commands apply once, a later batch sees a predecessor committed after its repeatable-read snapshot, mid-batch failure rolls back and acknowledgment-loss replay returns the committed receipt. It creates/drops only its generated database and leaves the configured application DB unchanged. These checks do not close P5-05 or P5-09.

### NOTE HTTP admission and durable dispatch (2026-09-26, subsequent checkpoint)

This supersedes the earlier internal-command-only async boundary above. Production admission is still guarded; the following transport is executable when the app is in test mode and async is explicitly enabled.

- **Observed / implemented**: `/api/study/sessions/<session_id>/batch` now admits NOTE/v4 batches; `commit?async=1` accepts the paired `study-commit.v3` envelope. Admission owns a single transaction under learner/session locks, validates the frozen wire/config/pins, requires contiguous batch and event sequences, rejects event-ID reuse, and prevents admission after a final or failed predecessor. A repeated ID must match its durable request hash. A committed admission is recoverable even when the external queue push is lost; HTTP 202 means accepted, never committed.
- **Evidence**: `app/validators/study_note_batch.py`, `app/services/study_note_batch_transport_service.py`, NOTE dispatch/recovery in `study_worker_service.py`, the shared admission branch in `study_session_service.py`, and `tests/test_study_note_batch.py`. The canonical Note command and legacy Card worker remain separate branches.
- **Queue boundary / alternatives**: Carrying a full second executable payload in Redis would require comparing two copies and also expose the session bearer token there. The selected `study-note-batch-job.v1` carries only the durable session/batch/user/wire/hash identity, plus non-authoritative delivery metadata. The worker rejects unexpected executable fields and reads the actual client log from MySQL. Retry count remains the typed DB column, not queue metadata. No second outbox or authority table is introduced.
- **Worker outcomes**: New actions and their batch receipt commit atomically through the canonical command. A pending predecessor defers the job without consuming retries and republishes its lost predecessor hint even if the queue is nonempty. Recovery orders equal-time rows by session and batch sequence before UUID, which matters with MySQL DATETIME(0). Permanent canonical conflicts are persisted as failed with a typed error; transient faults retain the existing durable retry budget; uncertain COMMIT honors the completed row. A synchronous commit cannot overtake an admitted NOTE stream (`SESSION_HAS_ASYNC_BATCHES`).
- **Status contract**: Authenticated `GET /api/study/sessions/<session_id>/batch/<batch_id>` returns `study-batch-status.v1`, with enqueued/completed/failed status, sequence, event count, attempt count and final marker. Completed NOTE responses include the hash-checked canonical batch receipt. Failed responses expose a safe error code, not raw database driver/SQL text. Owner/session checks and `Cache-Control: no-store` apply; a corrupt receipt yields an error, not success. This endpoint is distinct from the still-pending continuation-aware **session** status reader.
- **Storage / migration implications**: The persisted payload uses existing MySQL TEXT, so NOTE admission enforces a **60 KiB UTF-8 encoded JSON limit**, independent of the broader HTTP 5 MiB limit. Nonfinite JSON and submitted NOTE final states are rejected. Cumulative session replay remains bounded to 5,000 events/5,001 batches. No migration, enrollment, or production data change is part of this slice.
- **Potential concern / impact**: Session-level staleness still compares current authority with the original pin, so it would mistake this session's own completed batch for an external advance. The browser must also retain each in-flight batch until a durable receipt, not remove it on 202. Enabling production before these are integrated could interrupt resume or lose locally pending work; the production guard remains in force.
- **Unknowns / next gates**: Finish continuation-aware session status, frontend batch polling/restore/finalization, a deployed continuous consumer/readiness contract, periodic recovery fairness under a busy queue, real Redis faults and production-shaped contention. Test-gated HTTP/worker support is not P5-05 completion or production authorization.

The disposable MySQL probe now admits the NOTE batches through HTTP. It retains the two-connection canonical concurrency/current-read/rollback/uncertain-COMMIT checks, then uses a separate learner to inject a commit fault, lose all queue hints, start a fresh Python worker process, finish three batches/four actions, verify both sibling projections and the persisted retry count, and read the final receipt through the status endpoint. The configured application database is untouched; only the generated probe database is created/dropped. Real production Redis and a deployed continuous consumer are not exercised.

### Continuation-aware status and browser receipt retention (2026-09-26)

This checkpoint supersedes the session-status gap above, but does not close frontend async delivery or production readiness.

- **Observed / fixed**: Session status compared current tokens with the original pins, incorrectly marking the session's own completed nonfinal batch stale. `study_note_session_status_service.py` now verifies a contiguous admitted stream and the completed prefix, canonical receipt chain, and original command fingerprints using the shared pure frozen-log verifier. Current canonical Note state/token remains the authority; no pin is advanced and no ReviewEvent history is replayed to construct current state.
- **Read boundary**: Status takes learner/session and canonical vector locks in the same order as the writer, refreshes ORM rows on locking reads, and rolls back its read transaction on every exit. Missing tokens fail with `AUTHORITY_TOKEN_REQUIRED`; the reader cannot initialize or repair them. Tests intercept SQL to prove repeated status checks perform no inserts, updates or deletes. Every Note pinned in the lease is checked, including Notes untouched by completed batches. An external advance, epoch change, malformed/rehashed payload or corrupt receipt still fails closed. Terminal batch receipts remain historical after later external reviews.
- **Contract**: The existing `study-session-status.v1` adds `batch_stream` (`study-note-batch-stream.v1`) with admitted/completed/pending counts, completed event count, failed batch ID and final batch ID/status. NOTE batch acknowledgment validates its receipt against the retained request, including its request hash and cumulative count, before removing the batch; an admitted stream cannot silently switch to synchronous commit. Existing UI layout/styles are unchanged.
- **Alternatives / trade-off**: A mutable session cursor would introduce another consistency boundary; keeping immutable pins plus verified existing receipts requires no schema change but adds bounded replay/read cost on status. A continuous consumer/readiness contract, busy-queue recovery fairness, real Redis faults, full MySQL/INT-03 coverage and production canary remain open.
